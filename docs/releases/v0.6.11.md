# RiffNotes v0.6.11

This release is a data-safety pass. It closes five ways a practice folder could lose metadata when
two people share it through Google Drive, and adds the test seam that makes sync verifiable without
a live Drive account.

## Highlights

- An unreadable `library.riffnotes.json` now stops the practice from opening instead of being
  treated as empty. Previously a damaged catalogue caused every recording to be re-assigned a new
  id, orphaning every note and section, and then overwrote the damaged file. The bytes are now left
  on disk, the practice is listed with the reason it cannot be opened, and one bad folder no longer
  prevents the rest of the band folder from loading.
- Portable metadata (`library.riffnotes.json`, `.riffnotes.<user>.bandnotes`,
  `.riffnotes.<id>.sections.json`) is written to a temp file and renamed into place, so an
  interrupted write can no longer leave a truncated file.
- Catalogue entries for takes whose audio is not present locally are retained rather than pruned.
  On a partially synced machine, opening a practice used to strip those entries and the next upload
  pushed the reduced catalogue over the complete copy, destroying titles and Best Take flags.
- Google Drive uploads now send the local modification time. Without it the remote timestamp never
  matched the local one, so every locally authored file re-uploaded on every sync and change
  detection could never converge.
- Downloads no longer overwrite a local file that is newer than the remote copy. Downloading before
  uploading previously replaced newer local notes with an older remote version, silently. Protected
  files are reported in the sync summary; pass the override to force a restore.
- Downloads stream to a temp file and rename into place, so an interrupted download no longer leaves
  a truncated file where a valid recording is expected.
- File comparison uses a two-second tolerance instead of exact timestamp equality, which no longer
  mis-reports files as changed across exFAT (2 s granularity), NTFS (100 ns), and Drive
  (milliseconds).
- `mixed_Down` is excluded from sync, so archived multitrack sources are no longer uploaded. The
  skip rules for both sync directions are now a single shared implementation.
- Fingerprint chroma weighting is corrected. The configured weight was applied to each of the twelve
  pitch-class bins, making chroma roughly 28% of the score — the largest single group and the
  opposite of the documented intent. It is now divided across the bins, which puts the chroma group
  at roughly 3.2% with the default profile. See the note below before judging match quality: this
  change makes the code match its comment, but the comment may not describe the better setting.

## Internal

- Google Drive sync is split into `drive_file_store.dart` (interface), `drive_api_file_store.dart`
  (Drive API adapter), and `drive_folder_sync.dart` (algorithms). `google_drive_sync.dart` keeps
  OAuth and delegates. The public API used by the app is unchanged.
- Added `test/fake_drive_file_store.dart`, an in-memory store that lets folder sync be tested with
  no network and no Google account.
- Added `docs/technical-reference.md`, a feature-by-feature reference covering the invariants, the
  on-disk data model, and the reasoning behind non-obvious design decisions.
- Added `docs/manual-test-plan.md`.

## Notes

- **Fingerprint weight profiles saved before this release no longer mean the same thing.** The
  chroma group went from roughly 28% of the score to roughly 3.2% with defaults. Setting the chroma
  weight to **`1.44`** reproduces the previous scoring exactly (1.44 ÷ 12 = the old 0.12 per bin),
  so the two can be compared directly. Step 10 of [the manual test plan](../manual-test-plan.md)
  walks through the A/B. If the old weighting matches better on real rehearsal audio — plausible,
  since chroma carries song identity while the envelope features largely describe mic placement and
  room — then the default profile was calibrated against the bug and should be raised, rather than
  the fix reverted.
- **Upgrading does not require clearing any fingerprint data.** Feature extraction is unchanged, so
  cached fingerprints under `.riffnotes-cache/` remain valid and `_cacheVersion` is deliberately not
  bumped; clearing them only forces a needless re-decode. Re-running matching replaces pending
  suggestions by itself. Avoid *Clear generated cache for selected practice* and the
  fingerprint-state clear when the goal is just to re-match: both also delete accepted and ignored
  decisions, which are user judgements that cannot be recomputed. Learning examples are unaffected —
  `adjustmentFor` reads only the accept/ignore flag and the target, never the stored confidence.
- The Drive `modifiedTime` fix has not been confirmed against a live Google account. To verify, sync
  a practice twice in a row: the second run should report 0 copied. If it copies everything again,
  the API is not honouring the supplied timestamp and a different change key is needed.
- Two people editing the same title or section between syncs still resolves to one winner. The
  newer-wins rule prevents an older copy from overwriting a newer one, but the catalogue and
  sections files remain shared rather than per-user.
